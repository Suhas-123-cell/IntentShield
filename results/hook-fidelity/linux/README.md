# The `ps`-free detector's Linux `/proc` reader, run once in a container (lane r8-close, round 8; PID 1 fixed and re-run in round `r8fix`, see the end)

Question: the round 7 critic said the Linux `/proc` reader of `translation._ancestors()` was never run on Linux. This directory is that run: a local Docker container (`python:3.12-slim`, digest in `docker-meta.json`, kernel `6.12.76-linuxkit aarch64`, Docker 29.5.2), **`--network none`**, root filesystem read-only
(`--read-only --tmpfs /tmp:exec`), worktree mounted read-only. **No harness was launched.** The image has no `ps`, so the reader is the only source that can work (`ps_in_image: absent`). Code: `benchmarks/hook_fidelity/linux_probe.py`, tests `tests/test_hook_fidelity_linux_probe.py`. Code under test: `5bd06eb`.

Files: `matrix.jsonl`, `hidepid.jsonl`, `pid1.jsonl` (37 rows, field `round: r8`, `group`), `rows.jsonl` (all), `table.md`, `summary.json`, `docker-meta.json` (image digest, versions, the container commands and exit codes), `pytest-linux.txt` and `pytest-linux-pid1.txt` (the unit tests inside the container).
Reproduce: `linux_probe.py docker results/hook-fidelity/linux --deps <dir of pytest's pure-Python packages>` (needs Docker and the image).

**How the trees are built.** A dummy "harness" process named `claude` (a copy of `bash`, so `claude -p -c '<hook>'` has its flags first like a native build) or a Python script named `claude`, `codex` or `gemini` (the node-launcher form: program name in the second word) starts the hook as a child through `sh -c`; the hook is
`linux_probe.py hook`, which calls `translation._ancestors()` and `translation.detect_mode()` and writes the result. Variants: with and without the headless flag (`-p`, `exec`); under a pty from util-linux `script` and without one (`setsid`, stdin `/dev/null`); a deeper tree (`env`, `timeout`, extra `sh -c` layers);
no harness among the ancestors; `INTENTSHIELD_ANCESTRY_SOURCES=ps` (the one reader the image lacks) and `=proc`. **The ground truth of every case is how the tree was built**, as in the round 7 pty lane: a row shows the reader reads the tree it is given, not that the detector's rule is right for a real harness.

**Results (every row is one launch of one tree, deterministic, n=1; "agree" = the detected mode is the constructed one AND its `how` text names the constructed reason).**

* In the matrix the terminal is read from `/proc/<pid>/stat` as `136:0` (a pts) under `script` and `?` without a pty; `-p` and `exec` are read from `/proc/<pid>/cmdline`, native and node-launched alike (unlike macOS, where a node process that retitles itself hides its arguments, see `../compare/README.md` round 8). The reader took 0.10 to 0.19 ms per read.
* **Finding: a harness that is PID 1 is never seen.** `_walk` stops as soon as the process it just read has a parent of pid 1 or less, so PID 1 itself is not read. In the 8 `pid1` cases the chain is one `sh` long, complete, and the harness is "not found among the ancestors", so the mode is `headless`. The 4 unattended cases and the 2 `-p` cases under `-t` get the right mode for the wrong reason (6/8 mode equal); **the 2 interactive cases
  (`docker run -it image claude`, flag-less, with a pty) are read `headless` where a person is present**, which for an ask is the refusing direction (the person loses one prompt), not a run-through. The cause is the `found[0] <= 1` stop in `translation._walk` and the test that pins it (`test_a_walk_over_proc_stops_at_init_and_is_complete`), written for macOS, where pid 1 is `launchd`. Not fixed here: a one-line change is to
  stop at ppid 0 on Linux and read pid 1. A real harness is rarely PID 1 (a container normally has a shell or an init above it), so this is a corner, found by constructing it.
* **Unit tests inside the container** (`tests/test_translation_ancestry.py` and `tests/test_wrap_hook.py`, `--noconftest` because the repo's `conftest.py` imports `fastapi`, which the image does not have and the network is off): **75 passed, 2 skipped** with `--init` (`pytest-linux.txt`; the 2 skips are the macOS-only `libproc` tests; the Linux-only
  `test_the_real_proc_reader_agrees_with_the_os`, skipped on macOS, PASSED). Without `--init`, pytest is PID 1 and **1 of 77 fails** (`pytest-linux-pid1.txt`: `test_the_ancestry_is_read_with_no_runnable_ps` gets an empty chain because the test process has parent pid 0): the same mechanism as the finding above, here a property of the test setup.
  `--noconftest` removes the suite's isolation fixture, so this is not the full suite; on macOS the same two files without the fixture fail 1 test (`test_wrap_hook.py`) only because this session's own process tree contains a `claude`, which is the reason the fixture exists. The full suite (`pytest` with the fixture) was not run in the container.

**Reading the 28/28 (integration, from the round-8 critic).** One of the 28 rows is the `sources=ps` case in an image with no `ps`, where reading nothing is trivially right; quote it as **27/27 proc-source trees plus one control**. The expected values are the trees the probe built, so this is a self-consistency check of the reader, not an independent oracle, and the reader was never run under a real harness on Linux. Keep the PID-1 defect next to any "the Linux reader works" claim.

**Not done.** No harness ran in Docker; no real Claude, Codex or Gemini process was read on Linux, only dummy processes; a node-launched harness that retitles itself was not reproduced on Linux (no node in the image); no Alpine/BusyBox `ps`, no gVisor or other sandboxed `/proc`, no rootless or user-namespace case, no cgroup-v1 kernel; one kernel and one architecture (the Docker Desktop VM);
the `hidepid` case is one tree; the ground truth is construction. Cost: 16 containers in the committed run (`docker-meta.json`), plus about 22 earlier containers while building it (tool probes, dependency attempts for pytest, one full trial into a scratch directory); one image pull (`python:3.12-slim`, 205 MB); no paid service.

## Round `r8fix`: the PID 1 defect fixed and the run repeated (`r8fix/`)

The `pid1` finding above (a harness that is PID 1 is never read, so `docker run -it image claude` was read `headless`) is fixed in `translation._walk` (commit `cb55170`): on Linux the walk stops at parent pid 0 and reads PID 1; on macOS it still stops at `launchd` (a parent pid of 1 or less). The rows above (`round: r8`) are the **before** and are kept unchanged. `r8fix/` holds the whole run repeated on the fixed code (code under test `1c9fc19`, same image digest `sha256:aa943ce4...`, same flags, **`--network none`**, read-only root, 16 containers; no paid service; Docker Desktop had to be restarted first because its VM had died): `matrix.jsonl`, `hidepid.jsonl`, `pid1.jsonl`, `rows.jsonl`, `table.md`, `summary.json`, `docker-meta.json`, `pytest-linux.txt`, `pytest-linux-pid1.txt`, all with `round: r8fix`. Reproduce: `linux_probe.py docker results/hook-fidelity/linux/r8fix --deps <dir>` (the probe's `ROUND` constant is now `r8fix`).

| group | before (`r8`) | after (`r8fix`) |
|---|---|---|
| `pid1` (the harness is the container's PID 1; 4 with a pty, 4 without) | **0/8 agree, 6/8 same mode**; the 2 interactive cases read `headless` | **8/8 agree, 8/8 same mode**; the 2 interactive cases (`-it`, no flag, native and node form) read `interactive`; the 6 others read `headless` for the right reason (`-p` flag, or no pty); chain ends at the harness, source `proc`, complete |
| `matrix` | 28/28 | 28/28 (unchanged) |
| `hidepid` | 1/1 | 1/1 (unchanged) |
| all rows | 29/37 | 37/37 |

* **Unit tests in the container** (same two files, `--noconftest`): with `--init` **79 passed, 2 skipped** (was 75 passed, 2 skipped; the 4 new walk tests added and one rewritten). **Without `--init`** (pytest is PID 1): **78 passed, 3 skipped, 0 failed** (was 1 of 77 failed). The earlier failure is not a code defect: a test process that is PID 1 has no ancestors to read, so `test_the_ancestry_is_read_with_no_runnable_ps` now skips itself in that case; it is not evidence that PID 1 as the hook is handled. A second test (`test_a_failed_source_falls_through_to_ps_and_names_it`) used a fake `ps` tree that ended at parent 1, which the Linux walk now reads, and failed without `--init`; its tree now ends at parent 0 (the same would have failed on a Linux CI runner).
* **Scope and limits.** The same construction caveat holds: the ground truth is how the tree was built, only dummy processes ran, no real harness. The fix reads PID 1 on every Linux walk, so on a normal host the chain gains one more entry (`init`/`systemd`) and a host where `/proc/1` cannot be read (for example `hidepid`) now reads the walk as incomplete and the mode as `unknown` where it used to read complete; the `hidepid` row (harness unreadable) is unchanged. The `ps` source on Linux also stops at parent 0 now. macOS behaviour is unchanged and was not re-run beyond the unit tests (the `libproc` and `ps` paths still stop at `launchd`). The defect was a corner (a real harness is rarely PID 1).
